## 주제: LLM Deployment

## 개요
### LLM Inference
학습이 완료된 LLM에 입력을 넣어 토큰 단위의 출력을 생성하는 과정을 의미하고 Prefill과 Decode, 두 단계로 나뉜다.
#### Prefill
입력된 프롬프트를 한 번에 처리하고 KV Cache를 만들고, 첫 토큰을 만드는 단계이다. 연산량이 많고 compute-bound 성격이 강하다.

#### Decode
만들어진 KV Cache를 참고하면서 응답 토큰을 한 개씩 반복 생성하는 단계이다. 메모리 읽기 비용이 크고, memory-bound 성격이 강하다.

### LLM Serving
학습된 LLM을 API로 배포하여 사용자의 요청을 받고 추론을 수행하고 텍스트를 생성해 결과를 반환하는 시스템이다.

### vLLM
여러 유저의 요청을 동시에 처리하고 GPU 메모리 낭비를 줄여서 더 많은 응답을 생성하게 해주는 오픈소스 LLM 서빙 엔진이다.

## 서빙 기초 구조
### Streaming Response
생성된 응답 전체를 한번에 반환하지 않고 토큰이 생성될 때마다 순차적으로 반환하는 응답 방식이다.

### Context Length
모델이 한 번의 추론에서 처리할 수 있는 입력 토큰과 출력 토큰을 합한 최대 토큰 수를 의미한다.

### Max Tokens
LLM API에서 모델이 한 번의 요청에서 생성할 수 있는 최대 출력 토큰 수를 지정하는 파라미터를 의미한다.

### Structured Outputs
응답을 강제로 구조화하여 애플리케이션이 안정적으로 파싱할 수 있게 하는 기능이다.

## 추론 최적화
### KV Cache
이전 토큰들의 Key, Value 벡터를 재사용할 수 있도록 GPU 메모리에 저장해두는 캐시 구조이다.

### Continuous Batching
매 decode 스텝마다 완료된 요청은 배치에서 제거하고, 대기 중인 새 요청은 배치에 추가하여 배치 구성을 계속 갱신하는 스케줄링 기법이다.

### PagedAttention
KV Cache를 고정 크기 블록으로 나누어 저장하고 Attention 계산 시 필요한 블록을 참조하도록 만든 KV Cache 관리 방식을 뜻한다.

### Prefix Caching
여러 요청이 공통적으로 보내는 프롬프트(e.g., 시스템 프롬프트)의 앞부분의 KV Cache를 저장해두고 재사용하여 Prefill 계산을 줄이는 LLM 서빙 최적화 기법을 의미한다. 

### Throughout
LLM 서빙 시스템이 단위 시간동안 생성한 출력 토큰의 총량을 뜻한다.

### Latency
요청을 보낸 시점부터 첫 토큰이 도착(TTFT)하거나 전체 응답이 완료되기(Total Latency)까지 걸리는 시간을 의미한다.  
3가지 관점
- TTFT(Time To First Token)
- TPOT(Time Per Output Token) : 첫 토큰 이후, 출력 토큰의 평균적으로 생성되는 시간
- Total Latency

### Tensor Parallelism (TP)
하나의 LLM을 여러 GPU에 나눠서 올리고, 각 GPU가 모델 연산을 나눠서 병렬적으로 처리하도록 하는 방식이다.
